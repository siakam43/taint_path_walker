## 1. 背景与目标

taint-path-walker 是"外部接口识别 → 污点树生成 → 污点树安全检查"管线的中游 skill：

```
api-finder → api-cleaner →（拆分 + 算 TreeID）→ taint-path-walker → taint-tree-checker
```

- 输入：单个入口描述文件 `{TreeID}_entry.json`（api-cleaner 输出 `api_clean.json` 的一条，附上游算好的 TreeID）。
- 任务：从入口函数与初始污点出发，自行追踪污点传播路径，生成"污点树"——多条调用链，逐链附带调用点信息。
- 输出：`<project_dir>/.ethunter_out/taint-path-walker/{TreeID}.json`，格式与 taint-tree-checker 输入兼容（其可直接消费），供其做安全检查。
- 核心难点与研发重点：**C++ 特性处理**（虚函数/多态/重载/模板/构造析构/运算符重载/引用/智能指针等），确保污点传播不断链。
- 适用业务：嵌入式系统 HAL 层代码（用户态，上接嵌入式操作系统 service，下接内核驱动）。

**核心原则**：追踪完备优先——不到追踪上限不自行停止；宁可多枚举目标不可断链；不可臆造（无法追踪必须标注并写明已尝试的搜索方式）。

本 skill 不做漏洞判定（由下游 taint-tree-checker 负责），纯 markdown 单文件（`SKILL.md`），全部提示词中文。

## 3. 运行契约

### 3.1 用法

```
/taint-path-walker <project_dir> <entry_json>
```

- 两个参数均必填；缺失或只给一个时打印用法提示并结束。
- `<project_dir>`：待分析项目根目录。
- `<entry_json>`：单个 `{TreeID}_entry.json` 文件路径。**单入口模式**：每次调用只分析一条入口；批量调度由上游编排器循环调用。入口文件放在哪里由上游决定，skill 不扫描目录。

### 3.2 TreeID

TreeID = `{TreeID}_entry.json` 文件名去掉 `_entry.json` 后缀。由上游根据"函数名 + 函数所在文件"计算好，本 skill 只透传沿用；文件名不符合 `{TreeID}_entry.json` 模式 → 报错并结束。输出文件沿用同一 TreeID。

### 3.3 输出路径与预查重

- 输出目录：`<project_dir>/.ethunter_out/taint-path-walker/`（不存在则 `mkdir -p` 创建；创建失败降级到当前目录，确保有输出件）。
- 最终输出：`{TreeID}.json`；中间状态：`tmp/{TreeID}_state.json`。
- 预查重：`{TreeID}.json` 已存在 → 打印"该入口已有分析结果：{路径}，跳过分析。"并结束。支持上游重复调度。

### 3.4 环境适配

- **codegraph**：双方法检查 `<project_dir>/.codegraph` 存在时，后续代码搜索/调用关系查询优先使用 MCP 工具 `codegraph_explore`；不存在或环境未安装 codegraph / 未配置 MCP → 使用常规工具（grep/find/Read/ast-grep），不中断分析。
- **macro.json**：检查 `<project_dir>/.ethunter_out/macro.json` 存在则加载（编译期 `-D` 宏），`#ifdef` 分支判断时参考；不存在则跳过。
- **分析范围**（与 api-finder 一致，扩展 C++ 文件）：
  - 情况 A：`<project_dir>/.ethunter_out/clean_code.txt` 存在 → 按其行内路径（绝对/相对）构建 scope_files，去重、忽略不存在的文件。
  - 情况 B：无 clean_code.txt 但有 `<project_dir>/.ethunter_out/.etignore` → `find` 收集源文件后按 .etignore 规则排除。
  - 情况 C：都没有 → `find <project_dir> -type f \( -name "*.c" -o -name "*.h" -o -name "*.cpp" -o -name "*.cxx" -o -name "*.cc" -o -name "*.hpp" -o -name "*.hxx" -o -name "*.hh" -o -name "*.inl" -o -name "*.ipp" \)`。
- **路径规范**：与 taint-tree-checker 2.6 一致——分隔符统一 `/`；去掉前导 `./`；规范化后含 `..` 段的路径非法（报错并结束）。输出的 `file` 字段一律为相对 `<project_dir>` 的规范化路径（rel）。
- **文件存在性检查**：关键文件一律双方法交叉确认（`ls` + `Read` 工具），禁止使用 `test -f` / `[ -f ]`；两次结果不一致时用第三种方法取多数；两次都无输出或都报错 → 停止分析并报告。

## 5. 输入契约（`{TreeID}_entry.json`）

api-cleaner 输出 `api_clean.json` 的一条，例如：

```json
{"name": "func_a", "file": "/abs/path/to/a.c", "form": "parameter_input",
 "taint_data": "data/len", "local_module": "ISP 固件", "partner_module": "用户态 APP",
 "para_index": "1/2"}
```

| 字段 | 说明 | 本 skill 用途 |
|---|---|---|
| `name` | 入口函数名 | 入口函数定位、输出顶层键、链首元素 |
| `file` | 函数定义文件绝对路径 | 定位函数定义 |
| `form` | `parameter_input` / `channel_read` / `both` | 决定初始污点标记方式 |
| `taint_data` | 外部输入变量名或来源，多项 `/` 分隔 | 与 para_index 配合标记初始污点 |
| `local_module` / `partner_module` | 本模块/交互模块名称 | 仅作上下文理解，记入中间状态，不写入输出 |
| `para_index` | 0-based 参数索引，与 taint_data 逐项对应，信道项 `-1` | 初始污点标记的准绳 |

**校验规则（任一不通过 → 向用户报错并结束，不产出树文件，避免毒化下游）**：

1. 文件名符合 `{TreeID}_entry.json` 模式。
2. 文件存在（双方法确认）且为合法 JSON 对象（非数组）。
3. `name`、`file`、`form`、`taint_data`、`para_index` 五个字段齐全；`local_module`/`partner_module` 缺失容错。
4. `form` ∈ {parameter_input, channel_read, both}。
5. `para_index` 与 `taint_data` 按 `/` 分割后项数一致。
6. 入口函数源码可在 `file` 中（或全分析范围内）定位到函数定义。
7. `para_index` 合法性：每项必须为整数，且取值为 `-1` 或位于 `[0, 入口函数形参个数)` 区间内（越界、非法数值、非整数项 → 校验不通过）；同时与 `form` 相容：`parameter_input` 各项不得为 `-1`，`channel_read` 各项必须为 `-1`（`both` 允许混合）。形参个数按定义处书写的形参计数（隐含 `this` 不计入）。

## 6. 输出契约（`{TreeID}.json`）

```json
{
  "isp::hal::SensorCtrl::read_reg$ef4ebf80": [
    [
      {"func": "isp::hal::SensorCtrl::read_reg", "file": "src/sensor.cpp", "begin_line": "31",
       "calls": [
         {"callee": "isp::hal::bus_write", "line": "45", "taint_args": ["data"]},
         {"callee": "isp::hal::bus_write", "line": "60", "taint_args": ["len"]}
       ]},
      {"func": "isp::hal::bus_write", "file": "src/bus.cpp", "begin_line": "156",
       "calls": [{"callee": "isp::util::pack", "line": "160", "taint_args": ["buf"]}]},
      {"func": "isp::util::pack", "file": "src/util.cpp", "begin_line": "185"}
    ]
  ]
}
```

**规则清单**：

1. **顶层键**：`{入口函数限定名}${TreeID}`，与链首元素 `func` 严格一致（下游 taint-tree-checker 校验此项）。入口函数名取其源码定义处的限定名（C++ 为作用域限定名，C 为函数名）；解析不出限定名时回退使用输入 `name`，顶层键与链首元素保持同一取值。
2. **链元素**：`func`（函数限定名）、`file`（相对 project_dir 的规范化路径）、`begin_line`（函数定义起始行号，字符串），与 taint-tree-checker 输入格式一致。
3. **`func` 命名**：C++ 带命名空间/类作用域限定（`::` 连接，如 `isp::hal::SensorCtrl::read_reg`）；重载同名靠 `file` + `begin_line` 区分；lambda 记为 `<lambda@相对路径:行号>`；运算符记 `Class::operator[]` 形式。
4. **`calls` 字段**（仅调用方元素携带，末元素无此字段）：描述"本函数在哪些行把污点传给了本链中位于其后的元素"（含下一元素，以及被去重吞并的直调边对应的后继元素）。
   - `callee`：被调函数限定名，必须等于本链中位于该元素之后的某个元素（通常为下一元素）的 `func`。
   - `line`：调用点所在行号（调用方文件中），字符串。
   - `taint_args`：被调函数接收污点的形参名数组（形参定义名原文）；被调函数无污点形参、污点经非形参通道进入时为空数组——三种情形：①污点经全局/静态变量进入；②污点经接收对象（this 所指对象的成员态）进入；③污点经 lambda 捕获进入。
   - 同一元素对同一后继元素的多个调用点合并记录、按 `line` 升序；更短链被去重吞掉时，其调用点信息合并保留在幸存链上（信息不丢失）；不传污点的调用点不记录。`calls` 条目整体按 `line` 数值升序；同一 `line` 按 `callee` 字符串字典序；完全相同条目去重。
5. **链排序**：链数组按链的元素序列做字典序升序：逐元素比较（`file`、`begin_line`、`func`，均按字符串字典序）。
6. **去重（子序列包含）**：链 X 的函数序列是链 Y 的函数序列的子序列时，只保留 Y（极大链）；被吞并链的调用点信息合并进幸存链。例：`[a,b,c]`、`[a,b]`、`[a,c]` 只输出 `[a,b,c]`。
7. **边缘情形**：单元素链合法（`[[入口]]`，污点未跨函数边界时输出）；链数组必须非空。
8. **传播终止策略**：链元素必须能定位到项目内源码。污点传到项目外（无源码）或目标不可解析时，链截止于调用方函数；"传播去向 + 已尝试的搜索方式"记入中间状态的无法追踪清单，不臆造节点。
9. **写盘时机**：完整性自检通过后一次性写出（UTF-8，缩进 4 空格）；中断时只留中间状态，不产生半成品树。输出文件是判断 skill 执行成功的依据，最终必须存在。
10. **禁止在输出中出现绝对路径**：`file` 一律 rel 形态。

## 7. 污点追踪设计

### 7.1 初始污点标记

- `parameter_input` / `both`：按 `para_index` 中非 `-1` 项找到对应实参位置的形参，标记为初始污点；随后做**内部参数二次过滤**（语义判断）：框架/内核回调上下文指针、纯输出参数（只写不读）、常量类参数 → 剔除不追踪。
- `channel_read`（para_index 为 `-1` 项）：按 `taint_data` 描述在入口函数体内定位信道读取点（如 `msgrcv → msg_buf`、共享内存指针 `shm_ptr`），把读取结果变量标记为初始污点；定位不到 → 报错结束（输入与代码不符）。
- `both`：两部分都执行，合并初始污点集合。
- 全局/静态变量：污点写入后视为跨函数共享状态，树内后续函数读取视为污点传播，直至被覆盖（沿用 taint-tree-checker 4.1 规则）。判定基准以入口函数单次调用的执行先后为准（先写后读），与追踪处理顺序无关。
- `this` 本身非污点；其指向的成员按结构体成员规则。

### 7.2 工作队列追踪模型（惰性按需解析 + 工作队列）

- **工作项** = （链前缀 `path`，当前函数 `F`，F 内污点变量前沿 `frontier`）。初始工作项 = （`[入口]`，入口函数，初始污点集合）。
- **处理一个工作项**：完整阅读 F 全部代码（含所有分支），对 frontier 中每个污点变量追踪其在函数内的传播（详见 7.3 / 7.4），然后：
  - 发现把污点传给函数 g 的调用点 → 生成调用边（F→g、调用点行号、`taint_args`），入队新工作项（`path+[g]`，g，g 的新污点形参集合）；
  - 污点消亡（被非污点值覆盖、不再被使用）→ 该支线截止于 F；
  - 遇分发点（虚调用/函数指针等不可静态确定）→ 先解析候选目标（7.4），每个可解析目标各建一条调用边 + 工作项（受扇出上限）；解析结果写入 dispatch_cache，同一分发点不重复枚举；
  - 项目外无源码 / 目标不可解析 → 记入无法追踪清单（含已尝试的搜索方式），链截止于本函数。
- **调用点集合的归属**：元素 X 的 `calls` 收录 X 向本链中位于 X 之后的全部元素的传污点调用点（同一后继的多次调用合并、按行号升序）。被去重吞并的直调边（如 `[a,b,c]` 吞并 `[a,c]` 后 a 直调 c 的调用点）由幸存链中 a 的 `calls` 收录（c 位于 a 之后），信息不丢失。
- **分支处理**：条件分支使污点流向不同目标 → 各分支独立扩展（分支语境在追踪时理解并体现在调用点记录上）。
- **防环**：同一链中出现相同函数定义（同 `file`+`begin_line`）→ 停止延伸该分支，记录"环终止"；不影响其他分支。
- **路径 → 树 → 链**：叶节点路径构成污点树；所有工作项处理完后，从根出发的全部叶路径即候选链，经子序列去重得极大链。
- **校验不终止传播**：值经过校验/净化后仍来源于外部输入，继续追踪（是否安全由下游 taint-tree-checker 判定）；仅当污点值被非污点值覆盖、或完全消亡时终止。

### 7.3 污点传播模式

主体直接采用 taint-tree-checker 4.2 清单（直接传播 / 指针与内存操作 / 全局与静态变量 / 结构体与联合体 / 嵌入式特有），按"语义识别自定义封装函数（命名、参数模式、上下文）"原则执行；C++ 增量在 7.4。

### 7.4 C++ 特性处理专节（研发重点）

| # | 特性 | 处理策略 |
|---|---|---|
| 1 | 作用域命名 | 记录限定名（namespace/class 嵌套全前缀，`::` 连接）；重载同名靠 `file`+`begin_line` 区分 |
| 2 | 虚函数/动态派发 | 静态可确定（局部对象、`new` 具体类、明确类型的成员/全局对象、实参为具体类型）→ 精确解析唯一目标；不可确定（基类指针/引用、外部来源）→ 枚举全项目覆写实现：grep 派生类声明（`: public Base`/`override`）、多级继承沿链传递、多重/虚继承合并所有基类来源、基类非纯虚默认实现一并纳入；每个分发点受扇出上限；虚析构照常追踪；解析结果缓存 |
| 3 | 函数重载 | 按调用点实参数目/类型匹配签名；无法确定 → 列全部同名候选（受扇出上限） |
| 4 | 模板 | 按模板定义体追踪一次（不逐实例展开）；存在与调用匹配的特化定义时追踪特化 |
| 5 | 构造/析构/拷贝/移动 | 识别隐式调用：按值传参、返回对象、成员初始化列表、声明即构造（`Obj o(tainted)`）、临时对象；追踪构造体内污点去向（如参数存入成员） |
| 6 | 运算符重载 | `=`、`[]`、`()`、`->`、`+` 等识别为函数调用并追踪（`Class::operator[]` 形式）；智能指针 `->` 穿透到目标对象成员/方法 |
| 7 | 引用与别名 | `T&` 同指针处理；引用绑定建立别名，写经引用污染被引用对象；按引用捕获的 lambda 捕获项同规则 |
| 8 | lambda / 函数对象 | lambda 体按局部函数追踪，命名 `<lambda@相对路径:行号>`；`std::function`/仿函数经注册或赋值点解析目标（同间接调用规则） |
| 9 | 成员函数指针/回调 | 注册点/赋值点搜索解析目标，沿用"目标可确定必须追踪，不得以数量/深度为由放弃"规则；穷尽搜索无果才标注无法追踪 |
| 10 | 成员变量 | 非静态成员按结构体成员规则；static 成员按全局变量规则 |
| 11 | 类型转换/隐式转换 | static_cast/reinterpret_cast/const_cast/dynamic_cast/C 风格转换均不消除污点；带参构造的隐式转换、`operator T()` 转换运算符按函数调用追踪 |
| 12 | 其余 | 默认参数（调用点省略的实参取定义处常量，非污点）；`new T[tainted_n]` 尺寸污点传播；catch 块中污点变量的使用尽力纳入 |

**处理原则**：宁可多枚举目标（上限内）不可断链；静态可确定时精确解析，避免路径爆炸；模板不逐实例展开；外部库无源码不臆造。

### 7.5 追踪上限

- **深度上限**：自入口起（入口为第 1 层）单条链最长 10 层调用。第 10 层仍传播 → 停止延伸，链截止于边界节点，记录截断（函数名+行号+传播去向）。
- **扇出上限**：单个分发点（虚调用候选集/函数表/注册回调集/重载候选集）最多 20 个目标，按声明/注册/表项顺序取前 20 完整追踪；其余逐条记录（函数名+行号）。
- 数值与 taint-tree-checker 保持一致（10/20），保证管线行为可预期。
- **不到上限不要自行停止**：上限之内每个分支必须追踪至终态；截断 ≠ 终止——被截断分支之外的污点变量、其他分支照常追踪。

### 7.6 完整性与自检（末尾强制执行）

每个初始污点变量必须到达终态之一：

1. 传播停止（消亡/被非污点值覆盖）；
2. 离开项目范围（项目外无源码）；
3. 到达分发点且候选目标已完整枚举或截断有记录；
4. 无法追踪（有理由 + 已尝试的搜索方式）。

**自检项**：各分支是否有未入队项；调用点是否遗漏（回到调用方源码逐调用点核对）；链是否断链（污点去向未闭合）。自检不通过不得进入输出阶段。

## 8. 断点续分析与防遗忘

### 8.1 中间状态文件

`<project_dir>/.ethunter_out/taint-path-walker/tmp/{TreeID}_state.json`：

```json
{
  "tree_id": "ef4ebf80",
  "entry": { "…entry json 原文…" },
  "taint_marks": [ {"var": "data", "kind": "param", "index": 1} ],
  "phase": "tracing|done",
  "tree": {
    "nodes": [ {"id": 1, "func": "isp::hal::SensorCtrl::read_reg", "file": "src/sensor.cpp", "begin_line": "31"} ],
    "edges": [ {"from": 1, "to": 2, "call_sites": [ {"line": "45", "taint_args": ["data"]} ]} ]
  },
  "queue": [ {"path": [1, 2], "frontier": {"func_id": 2, "tainted_vars": ["data"]}, "status": "pending|in_progress"} ],
  "terminal_paths": [ {"path": [1, 2, 3], "end_reason": "传播停止|离开项目|深度截断|扇出截断|环终止"} ],
  "untraceable": [ {"func": "...", "line": "...", "target": "...", "reason": "源码缺失|目标不可确定", "tried": ["搜索方式1", "搜索方式2"]} ],
  "truncations": [ {"func": "...", "line": "...", "to": "..."} ],
  "dispatch_cache": [ {"site": "src/a.cpp:45", "candidates": ["..."], "resolved": true} ]
}
```

- **end_reason 取值说明**："离开项目"含项目外无源码、目标不可确定的无法追踪终止（明细见 `untraceable`）；"深度截断"/"扇出截断"为上限截断（明细见 `truncations`）。
- 截断明细（函数名+行号+传播去向）记入 `truncations`，与 `terminal_paths` 的"深度截断"/"扇出截断"对应。
- **保存时机**：每处理完一个工作项（扩展完毕、子项入队、标终态）立即落盘。
- **产出**：`terminal_paths` 是已完成链的原料，末尾统一做子序列去重 + 排序 + 组装输出。

### 8.2 恢复流程（入口四分支）

1. 校验输入（第 5 节规则）。
2. `{TreeID}.json` 已存在 → 打印跳过提示并结束。
3. `tmp/{TreeID}_state.json` 存在 → 加载，从 `queue` 中第一个 `in_progress`/`pending` 工作项继续；交叉校验 `queue` + `terminal_paths` 与 `tree` 规模自洽，不一致以 state 实际内容为准。
4. 都不存在 → 全新启动：创建目录、校验并标记初始污点、初始化状态文件。

### 8.3 防遗忘机制

1. **工作项粒度持久化**：中断最多丢一个工作项的进度。
2. **phase 追踪**：`tracing` → `done`；恢复入口唯一，避免漏判分支。
3. **关键数字概览**：队列剩余数、终态路径数、当前最大深度（写入 state，恢复时对照）。
4. **提示词层面**：检查清单 + 自检提醒（思维陷阱表），把"长任务不忘事"落到显式规则（见 8.4）。

### 8.4 SKILL 第七/九章内容要点（执行检查清单与自检提醒）

**执行检查清单（输出前逐项核对）**：`phase` 已为 `done`；`{TreeID}.json` 存在；每条链首元素与顶层键的入口函数名一致；每个非末元素的 `calls` 非空且 `callee` 均指向本链中位于其后的元素（含下一元素与被吞并的直调边）；调用点行号已回到调用方源码核对；子序列去重已执行；链排序规则已执行；截断/环终止/无法追踪项已全部记录；`file` 全部为相对规范化路径；单元素链与空传播等边缘情形已按 6.7/6.8 处理。

**自检提醒（思维陷阱，示例）**：

| 警惕信号 | 应对 |
|---|---|
| "虚调用候选太多，标注无法追踪吧" | 目标可确定必须枚举（上限内）；仅穷尽搜索无果才可标注，且写明已尝试的搜索方式 |
| "校验过了，污点清零，停止追踪" | 校验不终止传播；仅被非污点值覆盖或消亡才终止 |
| "同名函数当作一个" | 重载/覆写按 `file`+`begin_line` 区分，逐一追踪 |
| "函数名写短名更简洁" | 必须带作用域限定名（C++） |
| "这段代码看起来像漏洞，记下来" | 本 skill 不判定漏洞，只产出树 |
| "分支太多先记主路径，短的略过" | 上限内不得遗漏分支；被去重吞掉的短链信息须合并到幸存链的 calls |
| "状态文件等整条链完成再存" | 每个工作项处理完立即落盘 |

## 9. 错误与边缘情况

| 情况 | 处理 |
|---|---|
| entry json 非法/字段缺失/项数不一致/form 取值非法 | 报错并结束，不产出树 |
| 文件名不符合 `{TreeID}_entry.json` | 报错并结束 |
| 入口函数源码定位不到 | 报错并结束 |
| channel_read 定位不到信道读取点 | 报错并结束 |
| 分发点目标不可确定 / 项目外无源码 | 无法追踪清单（含已尝试搜索方式），链截止于调用方 |
| 深度/扇出超限 | 截断记录，链截止于边界节点；其余分支照常 |
| 环（同函数重复出现） | 停止延伸该分支，记录"环终止" |
| 输出目录创建失败 | 降级到当前目录创建，确保有输出件 |
| 输出已存在 | 跳过提示，不重复分析 |
| 关键文件存在性判断 | 双方法交叉确认（`ls` + `Read`，禁止 `test -f`） |
| 分析中断后重启 | 按 8.2 恢复流程续跑；结果应与直跑一致 |

### 10.1 用例覆盖

## 13. 术语表（提示词用词规范）

| 用词 | 含义 |
|---|---|
| 污点 / 初始污点 | 外部不可信数据 / 入口处标记的起始污点变量 |
| 污点源 | 入口参数或信道读取的数据来源 |
| 污点传播 | 污点在变量间、函数间的传递过程 |
| 污点树 | 从入口出发、与污点传播相关的调用图（多条链） |
| 链 / 链元素 | 一条污点传播调用路径 / 路径上的一个函数节点 |
| 调用边 / 调用点 | F→g 的传播关系 / F 中调用 g 的具体代码位置（行号） |
| 污点形参 | 被调函数接收污点的形参名（`taint_args`） |
| 分发点 | 需解析目标的不可静态确定调用（虚调用/函数指针/回调/重载候选） |
| 覆写 | 派生类对基类虚函数的实现（override） |
| 限定名 | 带命名空间/类作用域的 C++ 函数名（`::` 连接） |
| 工作项 / 前沿 | 队列中的追踪单元（链前缀+当前函数+污点变量） / 当前函数内活跃的污点变量集合 |
| 终态 | 污点追踪的终止状态（消亡/离开项目/已完整枚举/截断/无法追踪） |
| 截断 | 因深度或扇出上限停止延伸（≠终止，其他分支照常） |
| 环终止 | 同链中函数重复出现而停止延伸 |
| 无法追踪清单 | 记录了理由与已尝试搜索方式的未闭合传播去向 |
| 子序列去重 | 链 X 的函数序列是链 Y 的子序列时只保留 Y（极大链） |
